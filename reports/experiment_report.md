# 基于自主智能体的交换机安全审计系统：设计、实现与实验验证

**课题方向**：基于自主智能体 Agent 的网络设备隐蔽后门漏洞自动化挖掘  
**当前阶段**：系统原型实现与基础功能验证  
**实验日期**：2026-04-07

---

## 摘要

本报告记录了交换机安全审计智能体系统的当前实现进展。系统以 LangGraph 为编排框架，构建了"思考—执行—分析"的自主探测循环，能够通过多轮 SSH 命令交互自动发现需要跨多个配置项组合才能构成的复合攻击路径。在 Cisco DevNet 公开沙箱环境（IOS XE 17.15.1）的验证实验中，系统于 8 轮探测内提取 35 条安全事实，确认 4 条攻击链（1 条 Critical、2 条 High、1 条 Medium），并成功证伪 1 条初始假设路径，实现了从目标连接到报告生成的全流程自动化。

---

## 一、研究背景

交换机等网络设备的安全配置涉及认证策略、管理协议、二层防护等多个维度，任何单一配置项的缺陷在孤立看来危害有限，但多个缺陷的组合往往构成完整的可利用攻击路径。例如，"密码使用可逆编码"与"HTTP 管理界面无访问控制"分别只是中低级问题，两者叠加则意味着攻击者可以直接解码凭证并登录管理后台。传统基于规则的扫描工具逐条匹配配置项，缺乏跨项关联推理的能力，难以发现此类复合漏洞。

本研究的核心问题是：能否设计一个自主智能体，在不依赖预设规则的条件下，通过与目标设备的多轮交互，自动推断出这类需要多步骤组合才能形成的攻击路径？当前阶段的工作聚焦于回答这一问题的基础部分：在已知配置层面，系统是否能可靠地发现并验证复合攻击链。

## 二、系统设计

### 2.1 总体架构

系统采用 LangGraph 构建有状态的智能体图，核心执行循环为：

```
[开始] → think → act → analyze → [路由判断]
                                    ├── think（继续探测）
                                    └── report → [结束]
```

`think` 节点负责根据当前已知信息决定下一步执行哪条命令；`act` 节点通过 SSH 在目标设备上执行该命令并记录原始输出；`analyze` 节点从输出中提取安全事实，推断或更新攻击链假设，并生成下一轮的优先探测方向。路由函数在每轮 `analyze` 结束后判断是否继续循环，条件为：状态为 `running` 且未超过最大轮次限制（当前设定为 8）。

LangGraph 的检查点机制使每次状态转换均被持久化，支持审计过程的完整回放和状态时间旅行，这对于结果可复现性验证具有重要意义。

**[图①：工作流图截图]**

### 2.2 审计状态模型

系统的核心数据结构是 `AuditState`，其设计遵循"状态即审计日志"的原则——每个字段是可审计的一等事实，而非调试字符串。关键字段如下：

| 字段 | 类型 | 说明 |
|------|------|------|
| `command_history` | `list[CommandRecord]` | 所有命令的结构化执行记录，含原始输出、执行状态、时间戳 |
| `facts` | `list[Fact]` | 从命令输出中提取的安全事实，每条仅陈述一件事 |
| `attack_chains` | `list[AttackChain]` | 跨命令推断的复合攻击链，含置信度与支撑证据 |
| `next_probes` | `list[str]` | analyze 节点向 think 节点传递的优先探测命令列表 |

`Fact` 与 `AttackChain` 的关系是系统设计的核心：Fact 是原子单元，只陈述命令输出直接呈现的内容；AttackChain 是由 ≥2 条来自不同命令的 Fact 组合推断出的可利用路径。这一分层设计将"观察"与"推断"在数据层面严格分离。

### 2.3 命令知识库

所有可执行命令的唯一来源是 `switch_audit/knowledge/ios_xe_commands.yaml`，涵盖 11 个安全类别、61 条只读 `show` 命令，包括：设备身份与全局配置、二层网络与 STP、端口安全、管理协议（CDP/LLDP/HTTP/SNMP）、访问控制与认证、NTP、ACL 与路由、DHCP Snooping、加密与证书、日志审计。

知识库与推理逻辑完全分离——`think` 和 `analyze` 节点在运行时动态读取 YAML 文件内容并注入 Prompt，命令库的更新无需修改任何逻辑代码。

## 三、关键技术实现

### 3.1 证据质量约束

系统对事实提取有严格约束：每条 `Fact` 的 `raw_evidence` 字段必须逐字引自命令输出，不允许总结、推断或合并。若在输出中找不到可以逐字引用的文本，则该 Fact 不得创建。

这一约束的意义在于切断误报的传播路径：如果 Fact 本身允许包含推断，那么基于该 Fact 构建的 AttackChain 的置信度就失去了可验证的基础。`raw_evidence` 的逐字引用要求使每一条链的每一个步骤都可以追溯到设备输出的具体行，为结果的人工复核提供了完整的证据链。

### 3.2 目标导向探测机制

`next_probes` 字段实现了 `analyze → think` 的反馈回路。当一条攻击链被标记为 `speculative` 或 `likely` 时，其 `verification_needed` 字段中列出的命令会被汇总进 `next_probes`，`think` 节点在下一轮决策时优先从中选取。

这一机制使系统的探测行为从无差别覆盖转变为目标导向：一旦发现某条链的前提条件部分成立，系统会主动去执行最能提升（或否定）该链置信度的命令，而非随机切换探测方向。以本次实验为例，Trial 1 的 `show running-config` 发现了可逆密码与 HTTP 服务并存，系统随即将 `show ip http server status` 加入 `next_probes`，Trial 2 执行该命令后确认了 HTTP 认证方式为 enable 密码且无来源 IP 限制，链的置信度随之升为 `confirmed`。

### 3.3 攻击链置信度与证伪机制

攻击链的置信度遵循状态机：`speculative → likely → confirmed`，通常只升不降。`confirmed` 的判定标准是 `verification_needed` 为空列表——即链中每一个攻击步骤都已有来自实际命令输出的 Fact 支撑，不存在需要额外验证的环节。

系统同时支持置信度降级（`refuted`），但条件严格，需同时满足三个条件：新 Fact 来自实际命令输出（非推断）；新 Fact 直接否定链中某一关键步骤（而非仅弱化）；该步骤位于攻击路径的关键链路上（去除后整条链无法成立）。

在本次实验中，这一机制发挥了实际作用：系统在 Trial 1 基于 TACACS+ 密钥可逆这一事实，推断出"密钥泄露可能导致认证绕过"的假设链。Trial 3 执行 `show aaa servers` 后发现 AAA 基础设施不可达（命令返回空输出），系统据此将该链标记为 `refuted`，并在后续轮次中不再为其生成验证探测命令，避免了对已排除假设的无效资源消耗。

### 3.4 Type 7 密码算法解码

Cisco IOS 的 Type 7 编码使用固定 XOR 密钥表的可逆变换，任何持有配置文件的人均可即时还原明文。系统在 `switch_audit/tools/crypto.py` 中实现了该解码算法，并在 `analyze` 节点处理 `show running-config` 输出时自动调用：识别配置中的 `password 7 <ciphertext>` 模式，将解码结果作为 ground truth 直接注入 LLM 上下文。这使得相关 Fact 可以直接陈述明文凭证，攻击链的置信度无需额外命令验证即可达到 `confirmed`。

### 4.4 结果讨论

8 轮探测中，Trial 1 的 `show running-config` 产生了全部攻击链的初始假设，Trial 2–7 的后续探测均为验证性操作，将 4 条链从 speculative 逐步升至 confirmed。这一模式符合预期：全局配置是信息密度最高的单一命令，后续命令的价值在于精确验证特定假设，而非广谱扫描。

需要说明的是，当前系统发现的均为**配置层面的已知漏洞类**（可逆密码、缺失安全控制等），属于被动侦察范畴。系统能够确认"攻击的前提条件全部成立"，但尚未实现对攻击可执行性的主动验证（即实际尝试登录、实际发送畸形报文）。这是当前阶段与完整漏洞挖掘流程之间最主要的差距，将在后续工作中通过引入主动验证节点来补齐。

## 五、结论

本阶段实现了基于 LangGraph 的交换机安全审计智能体原型，核心贡献在于：通过 `next_probes` 反馈回路实现了目标导向的探测策略；通过 `raw_evidence` 逐字引用约束保证了证据的不可篡改性；通过 ≥2 source_command 成链规则将发现质量从单点问题提升至复合攻击路径；通过置信度证伪机制使系统具备了排除假阳性的自主能力。

在 Cisco IOS XE 17.15.1 环境的端到端实验中，系统在 5 分钟内完成了从连接到报告生成的全流程，发现 4 条已确认攻击链，结果可被独立复现验证。

## 六、后续工作

当前系统的主要局限在于缺乏主动验证能力——所有 `confirmed` 链仅代表"前提条件已确认"，而非"攻击已被执行验证"。下一阶段计划引入独立的 `verify` 节点，对置信度达到 `confirmed` 的链自动执行主动探测，将结果分类为 `confirmed_exploited` 或降级为 `likely`，从根本上缩短从发现到可利用性确认的路径。

在知识层面，当前命令知识库以静态 YAML 文件形式维护，计划向量化后支持 RAG 语义检索，以支持非 Cisco IOS XE 设备类型（如 Juniper JunOS、华为 VRP）的接入，实现知识层与推理逻辑的解耦。
